# Plan: Anomaly function and anomaly_rule alerts

Status: Done
Issue: https://github.com/fuseone-io/fusescope-mcp-server/issues/15, https://github.com/fuseone-io/fusescope-mcp-server/issues/16
PR: https://github.com/fuseone-io/fusescope-mcp-server/pull/17

## Context

FuseScope now evaluates the `anomaly` query function on `/api/v5/query_range` (fuseone-io/fusescope#420)
and `anomaly_rule` alert rules (fuseone-io/fusescope#421). The server advertised neither: the alert write
schemas narrowed `ruleType` to threshold and PromQL rules, and the result bounds inserted a default limit
that FuseScope refuses on the anomaly query.

FuseScope differs from the pinned SigNoz spec: anomaly rules take schemaVersion v1 only, while the
SigNoz spec, its `metric_anomaly` example and the generated `PostableRule` describe them as v2alpha1.

## Approach

- Query: `ApplyBounds` inserts no limit or order on a builder query carrying `anomaly`;
  `fusescope_query_metrics` sends no limit on it and reports that in its decisions. The functions
  parameter, the metrics guide and the builder-query descriptions teach the arguments, the response
  series, and the 400/413/429 refusals.
- Rules: the `ruleType` overlay offers `anomaly_rule`, keeps `condition.algorithm` and
  `condition.seasonality`, and stops requiring `evaluation`, `notificationSettings` and
  `condition.thresholds`, which a v1 rule leaves to FuseScope. The alert instructions and examples
  teach the v1 shape.

## Files to Modify

- `pkg/querybuilder/bounds.go`, `pkg/querybuilder/request.go`: anomaly queries stay unbounded.
- `internal/handler/tools/metrics_query.go`: no limit on the anomaly query, decisions note.
- `internal/handler/tools/query_param_descriptions.go`, `query_options.go`, `metrics.go`,

- `pkg/metricsrules/guide.go`: Anomaly Function section and example.
- `internal/handler/tools/alert_rule_types.go`, `alerts.go`: rule schema overlay and descriptions.
- `pkg/alert/resources.go`, `pkg/alert/examples.go`: Anomaly Alerts section and a v1 example.
- `README.md`, `manifest.json`, wire-catalog fixtures.

## Key Decisions

### 2026-11-17 — keep the SigNoz spec pin

- Decision: keep generating from `SIGNOZ_SPEC_REF`; teach FuseScope's anomaly behaviour through the
  existing overlay, descriptions and resources.
- Rationale: the generated types already carry the anomaly function and response series. Switching the
  generator to FuseScope's spec changes every generated artefact and needs its own decision.

### 2026-11-17 — drop the limit on the anomaly query in fusescope_query_metrics

- Decision: send no limit on query A when it carries `anomaly` and no formula, even when `limit` is
  passed, and say so in the decisions note.
- Rationale: FuseScope rejects any limit there, and clients often send the advertised default of 100.

### 2026-11-17 — relax the required list of the alert write schemas

- Decision: `evaluation`, `notificationSettings` and `condition.thresholds` are no longer required.
- Rationale: a v1 anomaly rule has none of them; FuseScope derives them and validates v2alpha1 rules.
